# 던전별 기록·진행도 개발 설계안

작성: 2026-10-18 KST. **검토용이며 아래 저장 구조·DB·플레이 기록 로직은 아직 구현하지 않았다.** 이번 적용은 월드맵 정보 팝업과 기존 입장/도움말 연결까지다.

## 권장 구조

던전의 고정 정보는 DB, 플레이 결과와 체크포인트는 savedata, 화면은 표시만 담당한다. 공통 키는 실제 씬 이름 `sceneName`으로 통일한다. 실제 프로젝트의 첫 씬 이름은 `DUNGEON_001`이고 기존 `Data/dungeons.json`에는 `Dungeon_001`로 되어 있다. 기존 키는 마이그레이션에서 실제 이름으로 치환하며, 단순히 모든 값을 소문자로 저장하지 않는다.

`Assets/Resources/Data/db.json`에 다음 던전 목록을 추가하고, GameDatabase의 sceneName 조회 함수를 통해 번호·이름을 가져오는 방식을 권장한다. 아래 이름은 예시이며 현재 목록의 이름은 `버려진 채굴장`이다. 이번 작업에서는 이름/DB를 바꾸지 않았다.

```json
"dungeons": [
  {
    "sceneName": "DUNGEON_001",
    "number": 1,
    "name": "서늘숲",
    "mapResourcePath": "Maps/DUNGEON_001"
  }
]
```

기존 DungeonDatabase/포인트의 dungeonId는 연결 어댑터로 유지한 뒤 같은 DB를 조회하도록 옮긴다. 던전 메타데이터를 두 JSON에서 각각 수정하는 구조는 피한다. 아직 씬/빌드 등록이 없는 던전은 화면에 표시할 수 있어도 입장은 비활성화한다.

## savedata 예시

기존 save_version 2를 3으로 올리고 던전별 누적 기록과 던전별 checkpoint를 분리한다. 아래는 기존 저장 파일 전체가 아닌 **추가/교체할 부분만** 보여 준다. 기존 골드·인벤토리·장비·현재 플레이 결과 필드는 유지한다.

```json
{
  "save_version": 3,
  "dungeon_records": {
    "DUNGEON_001": {
      "clear_count": 0,
      "best_clear_time_seconds": 3599,
      "best_hit_count": 399,
      "max_broken_traps": 0,
      "last_committed_clear_run_id": ""
    }
  },
  "checkpoint": {
    "DUNGEON_001": {
      "mapIndex": 0,
      "totalMaps": 6,
      "resumeRequested": false,
      "broken_traps_snapshot": 0
    }
  },
  "active_run": {
    "run_id": "",
    "sceneName": "",
    "pending_clear": false
  }
}
```

- `clear_count`: 정상적으로 완료한 플레이마다 한 번 증가. 기본 0.
- `best_clear_time_seconds`: 초 단위 실수로 보관, 기본 3599초(59:59). 표시할 때 분/초로 변환.
- `best_hit_count`: 기본 399. 클리어 시 최소값 갱신.
- `max_broken_traps`: 기본 0. 클리어 시 최대값 갱신.
- `checkpoint[sceneName].mapIndex`: 이번 플레이에서 체크포인트로 확정한 완료 맵 수. 0~N. 체크포인트에서 이어 갈 다음 맵의 0 기반 인덱스와 숫자가 같다.
- `totalMaps`: 실제 던전 맵 목록에서 계산한 N. 최초 클리어 전에도 내부에는 저장할 수 있지만 화면에는 `?`로 가린다.
- `resumeRequested`: 실제 재개 지점이 있는지를 별도로 표시. 클리어 후 mapIndex=N을 화면용으로 보존하더라도 재개 가능 상태로 취급하지 않는다.
- `run_id`와 `last_committed_clear_run_id`: 동일 플레이의 ClearScene 재진입/화면 갱신으로 기록이 중복 증가하지 않게 한다.

최고 기록과 이번 플레이 결과는 구분한다. 현재 `clear_time_seconds`, `hit_count`, `broken_traps`는 결과 화면/보수 계산용으로 계속 사용하고, 클리어가 확정될 때 던전별 기록에 반영한다. 클리어 전 포기한 플레이로 최고 기록을 갱신하지 않는다.

## 이벤트별 저장 시점

| 시점 | 처리 |
| --- | --- |
| 월드맵에서 포인트/팝업/도움말 열기 | 조회만 한다. 진행도나 기록을 초기화하지 않는다. |
| 입장 버튼으로 유효한 던전에 새 플레이 시작 | 새 run_id와 원래 던전 sceneName을 지정한다. 해당 던전 mapIndex만 0으로 초기화하고 totalMaps를 갱신한다. 기존 클리어 수/최고 기록은 유지한다. 실패한 씬 입장에는 저장하지 않는다. |
| 체크포인트 씬으로 이동 확정 | 원래 던전 sceneName으로 `GetNextMapIndexForCheckpoint()` 값을 저장한다. 현재 플레이의 해체 스냅샷과 재개 상태도 같은 시점에 저장한다. |
| 체크포인트에서 던전으로 복귀/사망 후 재개 | 기존 run_id와 mapIndex를 이어 간다. 새 플레이 초기화를 호출하지 않는다. |
| 체크포인트 없이 종료/중도 이탈 | mapIndex는 마지막으로 확정한 값 그대로다. 단순히 맵을 밟았다는 이유로 올리지 않는다. |
| 마지막 맵 완료 → ClearScene | 플레이 시간 flush와 원본 던전/run_id/결과 스냅샷을 먼저 확보한다. 유효한 완료 요청을 ClearScene 진입에서 한 번만 확정하고 clear_count/최고 기록/mapIndex=N/totalMaps를 함께 저장한다. 이어서 해당 던전의 재개 상태를 해제한다. |
| 결과 UI Refresh/닫기/보수 확인 | 누적 횟수를 다시 증가시키지 않는다. 기존 보수 중복 방지 로직을 유지한다. |

현재 `SaveManager.OnSceneLoaded(ClearScene)`는 checkpoint를 바로 지워 원래 던전 식별자가 사라진다. 따라서 이벤트 호출 순서에 의존하지 않도록 **클리어 전환 요청에서 원본 던전과 결과를 보관하고, ClearScene에서 이를 소비한 뒤 재개 상태를 정리**하는 순서를 권장한다. 마지막 맵의 일반 출구와 체크포인트 복귀 인덱스가 N에 도달해 ClearScene으로 가는 두 경로 모두 같은 완료 처리로 모은다. 유효한 완료 요청 없이 개발자가 ClearScene만 열면 기록하지 않는다.

기존 `ClearResultUI.Refresh()`는 여러 번 호출될 수 있어 횟수 증가 위치로 사용하면 안 된다. 저장 실패 시에는 같은 run_id로 재시도해도 한 번만 반영되도록 동일 저장 트랜잭션에서 기록과 확정 ID를 함께 쓴다.

## 진행도 표시 규칙

팝업은 clear_count가 0이면 `mapIndex / ?`, 1 이상이면 `mapIndex / totalMaps`를 보여 준다. 아래 N=6은 요청 예시다.

| 상황 | 표시 |
| --- | --- |
| 처음 시작 전/새 플레이 시작 | 0 / ? |
| 첫 맵만 경험하고 체크포인트 없이 종료 | 0 / ? |
| 2개 통과 후 체크포인트 도착 | 2 / ? |
| 최초 클리어 | 6 / 6 |
| 클리어 이력이 있는 던전의 새 플레이 | 0 / 6 |
| 새 플레이에서 2개 통과 후 체크포인트 | 2 / 6 |
| 4개 통과 후 두 번째 체크포인트 | 4 / 6 |

`MapSequenceManager2D`의 현재 맵 인덱스는 0 기반이다. 이미 `GetNextMapIndexForCheckpoint()`가 currentIndex+1을 반환하므로 저장된 mapIndex를 화면에서 다시 +1/-1 하지 않는다. 예를 들어 두 번째 맵까지 통과했다면 저장값과 표시값 모두 2다.

전체 맵 수는 DB에 수동으로 중복 입력하기보다 **맵 실행기와 같은 목록 공급자**에서 계산한다. `Assets/Resources/Maps/{sceneName}/map_*.json`의 유효한 맵만 동일한 순서로 읽도록 공통화하고 N을 저장한다. 현재 실제 파일은 DUNGEON_001이 5개, DUNGEON_002가 4개다. 실제 첫 던전은 현재 구성대로라면 5/5가 된다. 콘텐츠 변경 시 새 플레이 시작에 N을 새로 계산하고 저장 인덱스 범위를 검증한다.

## 기존 저장 파일 이행

1. 기존 파일의 백업을 보관하고, JObject 단계에서 버전을 확인해 새 타입으로 역직렬화하기 전에 변환한다. 기존 checkpoint 객체가 새 sceneName 사전과 다른 모양이므로 나중의 기본값 채우기만으로 처리하지 않는다.
2. 기존 checkpoint.sceneName이 유효하면 해당 던전 항목으로 옮긴다. 기존 mapIndex는 다음 맵 인덱스라 완료 수로 그대로 사용한다. -1은 새 구조의 0/재개 없음으로 정규화한다. 기존 resumeRequested/해체 스냅샷도 옮긴다.
3. 과거 던전별 클리어 횟수/최고 기록은 현재 저장 정보만으로 신뢰성 있게 복원할 수 없다. 새 기본값으로 시작한다. 기존 dungeon_status의 과제 플래그를 클리어 횟수로 변환하지 않는다.
4. 다른 던전과 골드·장비·아이템·현재 결과·기존 과제 정보는 보존한다. StatusSaveDefaults/검증과 저장소의 원자적 교체 로직도 같은 버전에 맞춘다.

## 구현 전에 검토할 정책

**첫 실제 클리어 기록은 기본값과 무관하게 실제 값으로 저장하는 것을 권장한다.** 최초 클리어가 70분 또는 피격 450회일 때 처음부터 min(3599,4200)/min(399,450)을 적용하면 실제로 달성하지 않은 59:59/399회가 최고 기록으로 남는다. 기본값은 요청대로 저장하되 clear_count==0인 첫 완료에는 실제 값을 대입하고 두 번째부터 min/max를 적용하면 이 문제가 없다. 기본값을 기록 상한으로 쓰려는 의도라면 이 정책은 조정해야 한다.

또한 월드맵의 입장은 요청 예시대로 **새 플레이 시작**으로 두고, 체크포인트 씬에서의 복귀만 이어하기로 구분할 것을 권장한다. 월드맵에도 저장 지점 이어하기가 필요하면 별도 버튼/선택으로 추가하는 편이 의미가 명확하다. 이번 팝업 UI는 기존 입장 동작만 유지하며 새 플레이 초기화는 아직 구현하지 않았다.

사망 시 시간/피격/해체 누적·롤백 정책과 보수 계산은 기존 동작을 유지하는 전제다. 새로운 누적 기록 때문에 전투/해체 판정이나 보수를 중복 처리하지 않는다.

## 승인 후 변경 대상과 검증

- Core: StatusSaveData/StatusSaveDefaults/저장 역직렬화 및 마이그레이션, GameDatabase/DB 던전 메타데이터.
- App: SaveManager, DungeonRunTracker2D, MapSequenceManager2D, 체크포인트 전환부, ClearResultUI 주변 완료 확정 경로, 팝업 데이터 공급자와 새 플레이 시작 연결.
- 공통 던전 맵 목록 조회와 던전별 기록 서비스로 갱신 지점을 모아 각 UI가 직접 저장 필드를 수정하지 않게 한다.
- 임시 파일/테스트 저장소에서 신규 저장·버전2 이행·N=6 표시 예시·첫 클리어가 기본값보다 나쁜 경우·더 나은/나쁜 재클리어·중복 ClearScene·체크포인트 재개/사망·여러 던전 격리·입장 취소/실패를 검증한다. 사용자 실제 저장 파일로 실험하지 않는다.

이 문서는 후속 개발 제안이며 DB/savedata/체크포인트/클리어 갱신은 사용자 검토 후 진행한다.
